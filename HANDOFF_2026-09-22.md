## What is implemented

### Shared driver and Ranking contract

- Active `CostDriver` records use stable `driverKey = sourceType:sourceId`; rank and display name are not persistence identities.
- The active calculation exposes the complete valid BOM and Routing finding population rather than permanently truncating to Top 10.
- Findings carry explicit `unfavorable`, `neutral`, or `favorable` impact.
- Candidate Selection remains the Ranking surface. It supports all findings, category and impact filters, selectable sort field/direction, source reference, data quality, and visible empty-filter states.
- Controllability remains a separate human classification.
- Any number of drivers can be selected for RCA; selection survives sort/filter changes and normal persisted session reload.

### RCA

- Selected drivers expose an inline RCA detail panel.
- The baseline record captures the extensible conceptual chain: `Factor`, `Root Cause`, and `Action`.
- RCA records preserve stable driver identity, source type/id, category, source reference, Base/Active parameters, cost gap, and update time.
- RCA is user-selected; the system does not auto-RCA every finding.

### Simulation

- Simulation no longer calls the official BOM/Routing mutation actions when editing What-If values.
- Scenario A/B/C inputs are local Scenario Drafts and remain isolated from Product, Reference, Current, Active, and Master Data values.
- Simulation requires explicit Ranking selection. With no selection, it shows a clear empty-selection state instead of silently choosing the first controllable driver.
- Multiple selected drivers are available in the Simulation selector and are evaluated one at a time. Scenario drafts are kept independently per driver so switching context does not overwrite another driver’s draft.
- Saved RCA action context is shown with the selected driver.
- Scenario values expose stable key, label, value type, unit, dependencies/formula metadata, and origin: `source`, `override`, or `calculated`.
- Additional supplied variables are preserved and shown in the collapsed Variable provenance detail instead of being silently discarded.
- Invalid/missing target inputs remain visibly invalid; no official-data promotion happens from editing a scenario.

## Deliberately deferred

These are not silently decided by this implementation:

- Final driver/RCA workflow status vocabulary.
- Combining multiple selected drivers into one combined Simulation scenario versus evaluating them separately.
- Exact financial formulas, units, and input/calculated roles for `Sale`, `COGS`, `Gross Profit`, `SG&A`, `OP`, and `Profit`.
- Full variable-authoring/configuration UX and the final variable registry.
- Scenario save/compare workflow, trial-record persistence, and any later adoption/promotion policy beyond the existing explicit button.
- Final category taxonomy and final Ranking column/layout decisions after realistic user use.
- Whether RCA remains inline or moves to a dedicated detail view.

## Resume / acceptance instructions

```powershell
git switch codex/snapshot-import-role-selector
git pull --ff-only origin codex/snapshot-import-role-selector
npm install
npm run build
npm run dev
```

Review in this order:

1. Master Data and Cost Breakdown context.
2. Candidate Selection: filter/sort all findings, mark controllability, select two or more drivers, and open RCA for each.
3. RCA & Simulation: confirm the selected-driver requirement, switch drivers, edit a Scenario Draft, expand provenance, and confirm Active values remain unchanged.
4. Decide the deferred status/formula/multi-driver questions before expanding the model further.

The next engineering change should begin only after human review records which deferred decisions are now ready to lock.
