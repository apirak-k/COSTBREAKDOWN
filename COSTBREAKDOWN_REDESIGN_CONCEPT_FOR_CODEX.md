# COSTBREAKDOWN — Before/After Redesign Concept & Proposed Implementation Direction

**Purpose:** Design / handoff report for discussion with Codex before the next implementation round  
**Project:** Prototype System for Product Cost Breakdown Analysis  
**Basis:** Current `COSTBREAKDOWN` repository, `Proposal-กลุ่ม81.pdf`, `breakdown_cost_web_final_logic_fixed.pdf`, `COSTBREAKDOWN_SYSTEM_LOGIC_SOURCE_OF_TRUTH.md`, and the latest project discussion  
**Status:** Proposed redesign direction — review before coding

> **Document precedence:** This is a historical redesign proposal. For current requirements use [`docs/REQUIREMENTS_INDEX.md`](docs/REQUIREMENTS_INDEX.md) and the page specifications. In particular, the current scope defers Export, keeps Material/Labor/Burden stable in Cost Breakdown, and uses Reference/Current terminology.

---

## 1. Why This Redesign Is Being Considered

The current prototype already supports cost calculation, cost breakdown, candidate selection, what-if simulation, trial validation UI, and basic version states. However, its current data model assumes that the two sides being compared mostly share the same BOM and Routing rows.

Examples from the current model:

```ts
BOMItem {
  consumption
  basePrice
  activePrice
  baseLoss
  activeLoss
}

RoutingStep {
  manning
  baseCap
  activeCap
  baseYield
  activeYield
}
```

This paired-field model is convenient when only numeric parameters change, but it becomes restrictive when the factory's real **Before vs After** comparison includes structural changes such as:

- a BOM item is added or removed;
- a Routing operation is added or removed;
- an operation changes sequence;
- an operation moves to another Work Center;
- the Work Center master/rates change;
- multiple process parameters change at the same time;
- the number of operations in Before and After is different.

The redesigned system should therefore **not require the Before and After structures to be identical**.

---

## 2. Factory-Oriented Operating Concept

The system should use the factory's natural language and workflow:

```text
BEFORE
  vs
AFTER
```

For this project, define them carefully:

### Before Snapshot
The reference/baseline cost-declare dataset used as the comparison starting point.

### After Snapshot
The later/current-condition dataset being compared with Before.

### Trial Actual
A separate concept used only after an improvement action is actually tested on the shop floor.

Therefore:

```text
Before vs After
= Cost / structure comparison

Predicted vs Trial Actual
= Improvement validation
```

**Do not use `After` and `Trial Actual` as the same thing.**

---

## 3. Main Architecture Decision — Snapshot vs Snapshot

Replace the assumption that Base/Active values must coexist inside the same BOM or Routing row.

Use two independent complete snapshots instead:

```text
BEFORE SNAPSHOT
├── Product
├── Work Center Master / Rates
├── BOM
└── Routing

AFTER SNAPSHOT
├── Product
├── Work Center Master / Rates
├── BOM
└── Routing
```

Then create a separate comparison layer:

```text
Before Snapshot
       ↕
Comparison / Diff Engine
       ↕
After Snapshot
```

Each snapshot must be independently valid and independently calculable.

This is the key design change.

---

## 4. No Database for the Project Scope

The proposed project deployment should avoid introducing a backend database unless it becomes necessary later.

Use:

```text
Excel files       = portable / persistent business data exchange
Browser state     = temporary working state / cache
Bundled project data = default demonstration / project product
```

### Intended behavior

- The project product is available as the initial/default dataset.
- The user can import another Excel dataset.
- The user can export a snapshot back to the defined Excel format.
- Browser storage may preserve the current working session, but it should not be considered the only permanent source of project data.

This reduces deployment complexity and is closer to the factory's existing working style.

---

## 5. One Excel Format, Two Import Roles

Prefer **one canonical Excel structure** rather than separate Before and After schemas.

Example conceptual workbook:

```text
META
PRODUCT
WORK_CENTER
BOM
ROUTING
```

When importing, the web application asks where the workbook should go:

```text
Import as:
[ Before ]
[ After  ]
```

This gives two practical workflows.

### Workflow A — Two independent files

```text
Import Before.xlsx
        ↓
Import After.xlsx
        ↓
Compare
```

### Workflow B — Start from Before and modify only the changes

```text
Import Before.xlsx
        ↓
Clone Before → After
        ↓
Edit After in the web
or Export After draft to Excel
        ↓
Change only what is different
        ↓
Re-import / continue
        ↓
Compare
```

This provides flexibility without forcing the user to rebuild the full After dataset manually.

## 6. Status Should Be Generated by the System

The comparison status should normally be a **derived result**, not a manually maintained Excel input.

The system compares the two snapshots and generates statuses such as:

```text
UNCHANGED
MODIFIED
ADDED
REMOVED
REORDERED / MOVED
NEED REVIEW
```

Recommended rules:

```text
Matched identity exists in Before and After
+ relevant values equal
→ Unchanged

Matched identity exists in both
+ one or more relevant values differ
→ Modified

Exists only in After
→ Added

Exists only in Before
→ Removed

Same operation identity but sequence changed
→ Reordered / Moved

System cannot match with sufficient confidence
→ Need Review
```

The UI can still allow a human to review or correct an uncertain match, but the user should not have to manually classify every row in Excel.

---

## 7. Identity and Matching Are Critical

Structural comparison only works if the system can determine whether a Before row and an After row represent the same business object.

### BOM

Prefer a stable business key such as:

```text
material / item code
```

If the same material may appear multiple times in one BOM for different purposes, introduce a stable BOM line identifier or an agreed composite key.

Do not use spreadsheet row position as identity.

### Routing

Prefer a stable operation identifier if the factory data provides one.

Conceptually:

```text
operationId
sequence
processName
workCenter
...
```

`sequence` should be treated as an attribute that may change, not as the operation identity.

Fallback matching rules may be added later, but ambiguous matches must become `NEED REVIEW` rather than being silently guessed.

---

## 8. Structural Change Comparison

A structural change is still part of the cost explanation. It should not simply disappear because there is no matching row on the other side.

### 8.1 Added Process

```text
Before cost = 0
After cost  = cost of the new operation
Gap         = After - Before
            = +After cost
```

Example:

```text
Inspection
Before: not present
After:  0.50 THB/pc
Status: Added
Gap:    +0.50 THB/pc
```

### 8.2 Removed Process

```text
Before cost = old operation cost
After cost  = 0
Gap         = After - Before
            = -Before cost
```

### 8.3 Added / Removed BOM Item

Use the same idea:

```text
Added material:
Before = 0
After  = current item cost

Removed material:
Before = previous item cost
After  = 0
```

Therefore, Added and Removed items/operations remain part of the total cost reconciliation.

---

## 9. Process Split / Merge — Keep the MVP Simple

Do not attempt to automatically infer complex process genealogy in the first implementation.

Example:

```text
Before:
Printing

After:
Printing A
Printing B
```

For the project MVP, it is acceptable to represent this as:

```text
Printing   = Removed
Printing A = Added
Printing B = Added
```

The user can add a structural-change note explaining that the old operation was split.

Future versions may support explicit relationships such as:

```text
Split
Merge
Replaced By
```

but these are not required for the first redesign.

---

## 10. Work Center Must Be a First-Class Master Relationship

A correction to an earlier interpretation is important here:

**Work Center is not merely a reporting/grouping label.**

In this project, the Work Center master/rate data is an upstream source used by Routing and can determine multiple values used in process cost calculation.

The current code already uses Routing `wc` to look up at least Labor Rate and Burden Rate. The redesigned model should preserve and strengthen this relationship rather than flattening Work Center into a display-only field.

Conceptually:

```text
WORK CENTER MASTER / RATES
        │
        ├── Labor Rate
        ├── Burden Rate
        ├── other confirmed WC-dependent calculation data
        │
        ↓
ROUTING OPERATION
        │
        ├── operation-specific inputs
        └── references Work Center
        │
        ↓
PROCESS COST CALCULATION
```

**Important:** Do not invent additional WC-dependent fields until they are confirmed from the factory / verified Excel model. The data model should allow the relationship, but the formula must stay consistent with verified project rules.

---

## 11. Three Work Center Change Cases Must Be Distinguishable

### Case 1 — Operation values change, WC stays the same

```text
Printing / WC01
Before Yield 95%
After Yield  90%
```

Result: operation is `Modified` because its own input changed.

### Case 2 — Operation moves to another WC

```text
Before:
Printing → WC01

After:
Printing → WC02
```

Result:

```text
Printing
Status: Modified
Work Center: WC01 → WC02
```

The cost engine must calculate each side using the corresponding snapshot's WC master data.

### Case 3 — Routing is unchanged but WC Master changes

```text
Before WC01:
Labor Rate  = X
Burden Rate = Y

After WC01:
Labor Rate  = X2
Burden Rate = Y2
```

All operations referencing WC01 may receive a cost impact even though their Routing rows themselves did not change.

This is why WC Master / Rate diff must be a first-class comparison branch.

---

## 12. WC as an Aggregate View

Because a structural process change can make row-by-row Routing comparison difficult to understand at a glance, Work Center is also useful as a higher-level aggregation.

Recommended drill-down:

```text
Total Cost Gap
│
├── Material Gap
│   └── BOM Items / Variables
│
└── Processing Gap
    └── Work Center
        └── Routing Operations
            └── Variables / Structural Changes
```

Example:

```text
WC01
Before Processing Cost = 12.00
After Processing Cost  = 10.80
WC Gap                 = -1.20

Open WC01
  ├── Process A Modified
  ├── Process B Removed
  └── Process C Added
```

WC aggregation helps show the larger process picture without requiring identical routing structures.

However, WC should **not** be used as the primary identity of an operation, because an existing operation may move from one WC to another.

## 13. Cost Calculation Should Run Per Snapshot

Refactor the cost engine conceptually from:

```text
calculateBaseAndActiveCost(one paired dataset)
```

to:

```text
calculateSnapshotCost(beforeSnapshot)
calculateSnapshotCost(afterSnapshot)
```

Then:

```text
compareCost(beforeCost, afterCost)
```

This removes the need for duplicated fields such as:

```text
basePrice / activePrice
baseLoss / activeLoss
baseCap / activeCap
baseYield / activeYield
```

Each snapshot row contains its own actual values:

```text
BOM row:
consumption
price
loss
...

Routing row:
capacity
yield
manning / resource input
workCenter
...
```

The Before vs After distinction belongs at the **snapshot level**, not inside every field.

## 14. Proposed Diff Layers

The comparison engine should produce separate diff objects rather than forcing UI components to infer changes directly from raw arrays.

Conceptual model:

```ts
type DiffStatus =
  | 'unchanged'
  | 'modified'
  | 'added'
  | 'removed'
  | 'reordered'
  | 'need_review'

interface BOMDiff {
  key: string
  status: DiffStatus
  before?: BOMItem
  after?: BOMItem
  changedFields: FieldDiff[]
  beforeCost: number
  afterCost: number
  costGap: number
}

interface RoutingDiff {
  key: string
  status: DiffStatus
  before?: RoutingOperation
  after?: RoutingOperation
  changedFields: FieldDiff[]
  beforeCost: number
  afterCost: number
  costGap: number
}

interface WorkCenterDiff {
  key: string
  status: DiffStatus
  before?: WorkCenterMaster
  after?: WorkCenterMaster
  changedFields: FieldDiff[]
  affectedOperationIds: string[]
}
```

Exact types can be adjusted by Codex after reviewing the existing repository.

---

## 15. Gap Reconciliation Rule

The comparison should always try to reconcile detail back to the total.

Conceptually:

```text
Total Gap
= After Total Cost - Before Total Cost
```

And the detailed explanation should reconcile back to that value:

```text
Material Gap
+ Labor Gap
+ Burden Gap
= Total Gap
```

Structural rows are included:

```text
Modified effects
+ Added effects
+ Removed effects
= branch gap
```

For an added row, use `Before = 0`.

For a removed row, use `After = 0`.

If a diff cannot be reliably attributed due to uncertain matching or an unverified formula, mark it clearly rather than forcing a false explanation.

## 17. Human Decision Must Remain in the Loop

The system should explain and organize the cost changes, but it should not automatically decide which factor is the best improvement target.

The redesigned system should:

1. calculate and explain the full Before/After gap;
2. collect changed factors / structural findings;
3. show impact and traceability;
4. let the human judge controllability, feasibility, scope, and practical relevance;
5. allow the user to select the factor to investigate;
6. perform RCA only after that selection.

`Top Driver` may be retained as a prioritization aid, but it must not silently become the automatic RCA target.

---

## 18. Candidate Findings Should Come from the Diff Layer

Current candidate logic is too closely tied to paired BOM / Routing rows.

After redesign, candidates should be generated from comparison findings.

Examples:

```text
M01 Price Modified
M01 Loss Modified
M02 Consumption Modified
M03 Material Added
Printing Yield Modified
Printing Work Center Modified
Inspection Operation Added
Old Packing Operation Removed
WC01 Labor Rate Modified
```

This means one BOM item or one Routing operation can produce more than one finding when multiple variables changed.

Human selection happens after all relevant findings are visible.

---

## 19. RCA, What-If, and Trial Should Remain Separate from Official After Data

Keep the following distinction:

```text
Before / After Comparison
        ↓
Selected Finding
        ↓
RCA
        ↓
Action
        ↓
What-If Prediction
        ↓
Trial Actual
```

What-if simulation must **not overwrite the official After snapshot**.

A scenario is a prediction, not official business data.

Trial Actual is also not automatically a new Before/standard dataset. A reviewed promotion/update workflow can be designed later if required.

## 23. Validation Requirements

Before calculation, validate at minimum:

- Product identity is present.
- BOM business keys are valid / not unintentionally duplicated.
- Routing operation identities are valid where available.
- Every Routing Work Center reference resolves to a Work Center in the same snapshot.
- Numeric fields required by verified formulas are present and valid.
- Units are valid.
- Effective dates / periods are visible where required.
- Source references are retained when available.

If information is uncertain, surface a warning / `Need Review` rather than silently inventing a mapping.

## 24. What Should Change in the Current Codebase

The following is an architectural direction for Codex to inspect, not an instruction to blindly rewrite all files.

### 24.1 Core Types

Current paired types such as:

```text
BOMItem.basePrice
BOMItem.activePrice
BOMItem.baseLoss
BOMItem.activeLoss

RoutingStep.baseCap
RoutingStep.activeCap
RoutingStep.baseYield
RoutingStep.activeYield
```

should move toward single-snapshot values.

Introduce snapshot and diff types.

### 24.2 Cost Engine

Refactor to calculate one snapshot at a time.

Current logic can be reused where formulas remain verified, but the engine should not depend on `base*` / `active*` fields living in the same row.

### 24.3 Comparison Engine

Add a dedicated layer responsible for:

- matching;
- Added / Removed / Modified / Unchanged / Reordered classification;
- field-level differences;
- cost effects;
- reconciliation;
- confidence / Need Review when matching is ambiguous.

### 24.4 Work Center Relationship

Make Work Center Master / Rates snapshot-specific and ensure Routing resolves its WC-dependent calculation data from the same snapshot.

### 24.5 Excel Parser / Exporter

Use the same canonical format for both sides. Import into a selected target snapshot.

Add clone-Before-to-After workflow.

### 24.6 Cost Breakdown UI

The UI should consume comparison results rather than calculating status ad hoc.

It should support:

```text
Total
→ Cost category
→ Work Center (for processing view)
→ BOM item / Routing operation
→ Field changes / structural status
```

### 24.7 Candidate Engine

Generate findings from the diff layer. Do not collapse every BOM item or process to only one candidate when multiple factors changed.

### 24.8 RCA / Simulation

Retain human selection.

Ensure scenario data is independent from the official After snapshot.

### 24.9 Trial

Keep Trial Actual separate from Before/After comparison data and persist it as an actual trial record when implemented.

## 26. Suggested Implementation Phases

Do not try to refactor the entire application in one large change.

### Phase 0 — Impact Analysis / Freeze Current Behavior

- Confirm active code path.
- Identify reusable calculation logic.
- Identify legacy duplicates.
- Document current Excel schema.
- Create/retain a safe checkpoint before structural changes.

### Phase 1 — Snapshot Data Model

Implement independent:

```text
Before Snapshot
After Snapshot
```

with Product, WC Master/Rates, BOM, Routing.

Do not implement the full UI redesign yet.

### Phase 2 — Per-Snapshot Cost Engine

Make the verified calculation work against a single snapshot.

Acceptance condition:

```text
calculate(beforeSnapshot)
calculate(afterSnapshot)
```

both work independently.

### Phase 3 — Diff / Matching Engine

Implement:

```text
Unchanged
Modified
Added
Removed
Reordered
Need Review
```

for BOM, Routing, and WC Master/Rate changes.

Add reconciliation tests.

### Phase 4 — Excel Import / Export

- One canonical schema.
- Import as Before / After.
- Clone Before → After.
- Export either snapshot.
- Preserve project default dataset.

### Phase 5 — Comparison / Breakdown UI

Build the factory-friendly Before vs After workflow.

Show structural statuses and cost effects clearly.

### Phase 6 — Candidate Integration

Move candidate generation to diff findings.

Preserve human decision.

### Phase 7 — RCA / What-If / Trial Cleanup

- explicit RCA data;
- action linked to RCA;
- simulations do not mutate After;
- real Trial records are persisted separately.

## 27. Minimum Acceptance Scenarios

Codex should create tests/fixtures covering at least the following.

### Scenario A — Numeric-only change

Same BOM and Routing structure; Price / Loss / Yield / Capacity changes.

Expected:

```text
Matched rows = Modified
Correct cost gaps
Total reconciliation passes
```

### Scenario B — BOM Added

After contains a new material.

Expected:

```text
Status = Added
Before cost = 0
Gap = After item cost
```

### Scenario C — BOM Removed

Expected:

```text
Status = Removed
After cost = 0
Gap = -Before item cost
```

### Scenario D — Routing Added / Removed

Expected structural statuses and conversion-cost reconciliation.

### Scenario E — Routing Reordered

Same operation identity, different sequence.

Expected:

```text
Operation remains matched
Status includes Reordered / Modified structural detail
Do not treat it as Removed + Added solely because sequence changed
```

### Scenario F — Operation changes Work Center

Expected:

```text
Same operation identity
WC01 → WC02
Status = Modified
Before calculation uses Before WC01 data
After calculation uses After WC02 data
```

### Scenario G — WC rate/master value changes only

Routing itself remains unchanged.

Expected:

```text
WC diff detected
Affected routing costs change correctly
Impact traceable back to WC change
```

### Scenario H — Process split

Before has one operation; After has two unrelated/new operation IDs.

MVP expected:

```text
Old operation = Removed
New operations = Added
```

No automatic split inference required.

## 28. Decisions That Should NOT Be Hard-Coded Yet

The following should remain configurable / `TO VERIFY` until confirmed with factory data or the verified mathematical model:

- exact fallback Routing matching key when no stable operation ID exists;
- whether one material code can appear multiple times and therefore needs a stable BOM line ID;
- all WC-dependent fields beyond currently verified calculation data;
- separate labor runtime vs machine/burden runtime if factory rules differ from the current Excel model;
- how formal snapshot approval / locking should work;
- whether structural `Reordered` should be a top-level status or a flag under `Modified`;
- how future Split / Merge relationships should be represented;
- whether Excel itself should contain a snapshot-role field or the role should exist only in the import UI.

Codex should ask / flag these instead of inventing factory rules.

---

## 29. Key Design Principles

1. **Before and After are complete independent snapshots.**
2. **Do not require identical BOM or Routing structures.**
3. **Compare structure first; do not silently discard Added or Removed rows.**
4. **A structural change can still have a calculable cost effect.**
5. **Work Center is a first-class master dependency for Routing calculations.**
6. **WC can also be used as an aggregate process view, but not as operation identity.**
7. **Use stable business identities, not spreadsheet row numbers or sequence alone.**
8. **Generate comparison status from the two snapshots.**
9. **Keep Excel as the portable data exchange for the project instead of adding a database.**
10. **Keep human judgment for candidate selection.**
11. **RCA explains why a selected factor changed; diff explains what changed.**
12. **What-if and Trial must not overwrite official After data.**
13. **All detailed effects should reconcile back to the total cost gap where the verified formula permits.**
14. **Do not invent factory calculation rules. Mark uncertain logic for verification.**

## Final Intent

The redesign is not intended to make the system more complicated for the user.

The goal is the opposite: keep the factory-facing workflow simple — **Before vs After** — while making the underlying data model flexible enough to explain real changes in both **numbers** and **process structure**.

The core technical idea is:

> **Calculate two independent snapshots, compare them explicitly, classify structural and numeric changes, and only then continue into cost-driver selection and improvement analysis.**
